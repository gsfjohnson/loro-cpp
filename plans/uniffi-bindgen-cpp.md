# Plan: Build Loro as a C++-consumable library via `uniffi-bindgen-cpp`

## Context

[Loro](https://github.com/loro-dev/loro) is a Rust CRDT library. The official [`loro-ffi`](https://github.com/loro-dev/loro-ffi) crate exposes the full surface (LoroDoc, six containers, subscriptions, awareness, ephemeral store, undo, fractional index, version vectors, JSON path) via UniFFI — the same source of truth that drives `loro-swift`, `loro-cs`, `loro-go`, and the React Native binding.

Rather than hand-write a parallel C ABI wrapper, this project uses [NordSecurity/uniffi-bindgen-cpp](https://github.com/NordSecurity/uniffi-bindgen-cpp) to **generate idiomatic C++ bindings directly from `loro-ffi`'s UniFFI definitions**. Net result: zero hand-written Rust glue, zero hand-written C++ wrapper for the core surface — when upstream `loro-ffi` adds a method, we regenerate. The shape of our resulting C++ API matches `loro-swift` 1:1.

A small hand-written `loro_ext.hpp` ergonomics layer is added on top, mirroring what `loro-cs` does in C# (lambdas-as-callbacks, conversion helpers for `LoroValueLike`/`ContainerIdLike`, unified `insertContainer` shortcuts). The build is wired through CMake + Corrosion so a single `cmake --build` produces the final `loro::loro` target.

Trade-offs accepted vs. the cbindgen alternative:
- **C++20 is mandatory** (uniffi-bindgen-cpp generated code requires it).
- **Plain-C consumers are not supported** — output is C++ only.
- **Three-way version pinning** is required across `loro-ffi` ↔ `uniffi` ↔ `uniffi-bindgen-cpp`.
- We lag upstream by whatever delta exists between the latest `loro-ffi` and the latest `loro-ffi` whose `uniffi` version has a matching `uniffi-bindgen-cpp` release.

## Pinned version triple (verified against crates.io and the NordSecurity tag list)

| Component | Pinned version | Why |
|---|---|---|
| `loro-ffi` | **`=1.10.3`** | Latest `loro-ffi` whose `uniffi` dep pairs with a released `uniffi-bindgen-cpp` |
| `uniffi` | `=0.28.3` (transitive via `loro-ffi`) | Required by `loro-ffi 1.10.x` |
| `uniffi-bindgen-cpp` | **`v0.7.3+v0.28.3`** (git tag) | Latest generator release on the 0.28 line |
| `loro` (Rust) | whatever `loro-ffi 1.10.3` resolves | Transitive |
| Latest available upstream `loro-ffi` | `1.11.2` (uniffi 0.31.1) | We trail this until NordSecurity ships a `+v0.31.x` release |

A bump to `loro-ffi 1.11.x` is gated on `uniffi-bindgen-cpp` releasing a `v0.29+` or `v0.31+` build. Tracked as a single follow-up issue; bump is a one-line `Cargo.toml` change plus regenerating headers.

## The Rust shim — why it's needed and what's in it

`loro-ffi` on crates.io is published as an **rlib** (no `crate-type` set), which can't be linked into a C++ application. The shim crate `loro-cpp-rs` exists solely to re-package it as a `staticlib`:

```toml
# loro-cpp-rs/Cargo.toml
[package]
name = "loro-cpp-rs"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["staticlib"]

[dependencies]
loro-ffi = "=1.10.3"
```

```rust
// loro-cpp-rs/src/lib.rs
// Re-export so uniffi-bindgen-cpp can find type metadata in our staticlib.
pub use loro_ffi::*;

// Force the linker to retain loro-ffi's #[no_mangle] scaffolding symbols
// when producing the staticlib. Without this reference, dead-code elimination
// can drop them since nothing in `loro-cpp-rs` itself calls them directly.
#[used]
static FORCE_LINK_LORO_FFI: fn() -> String = loro_ffi::get_version;
```

That `#[used]` static is the standard force-link trick for transitively-depended FFI symbols. If symbol stripping still happens at the linker stage, fall back to `--whole-archive` in the C++ link step (Linux/macOS) / `/WHOLEARCHIVE` (MSVC). CMake handles both via Corrosion's link options.

## Build wiring (CMake + Corrosion + bindgen invocation)

```cmake
cmake_minimum_required(VERSION 3.22)
project(loro-cpp LANGUAGES CXX VERSION 0.1.0)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

include(FetchContent)
FetchContent_Declare(
    Corrosion
    GIT_REPOSITORY https://github.com/corrosion-rs/corrosion.git
    GIT_TAG v0.5.1
)
FetchContent_MakeAvailable(Corrosion)

# 1. Build the Rust shim as a staticlib via Corrosion.
corrosion_import_crate(
    MANIFEST_PATH ${CMAKE_CURRENT_SOURCE_DIR}/loro-cpp-rs/Cargo.toml
    CRATE_TYPES staticlib
    PROFILE release
)

# 2. Install uniffi-bindgen-cpp (pinned tag), then run it against the staticlib
#    in library mode. Output goes into ${CMAKE_BINARY_DIR}/generated.
include(cmake/uniffi_bindgen_cpp.cmake)
uniffi_generate_cpp_bindings(
    TARGET          loro_cpp_rs                            # Corrosion-imported
    GENERATOR_TAG   v0.7.3+v0.28.3
    OUT_DIR         ${CMAKE_BINARY_DIR}/generated
    OUTPUT_HEADER   ${CMAKE_BINARY_DIR}/generated/loro.hpp
    OUTPUT_SOURCE   ${CMAKE_BINARY_DIR}/generated/loro.cpp
)

# 3. Build the public library: generated C++ + ergonomics header.
add_library(loro STATIC ${CMAKE_BINARY_DIR}/generated/loro.cpp)
add_library(loro::loro ALIAS loro)
target_include_directories(loro PUBLIC
    ${CMAKE_BINARY_DIR}/generated
    ${CMAKE_CURRENT_SOURCE_DIR}/include
)
target_link_libraries(loro PUBLIC loro_cpp_rs)
target_compile_features(loro PUBLIC cxx_std_20)

# Force-include all symbols from the Rust staticlib so UniFFI scaffolding
# survives linker GC.
if(MSVC)
    target_link_options(loro PUBLIC /WHOLEARCHIVE:$<TARGET_FILE:loro_cpp_rs>)
elseif(APPLE)
    target_link_options(loro PUBLIC -Wl,-force_load,$<TARGET_FILE:loro_cpp_rs>)
else()
    target_link_options(loro PUBLIC
        -Wl,--whole-archive $<TARGET_FILE:loro_cpp_rs> -Wl,--no-whole-archive)
endif()

if(BUILD_TESTING)
    enable_testing()
    add_subdirectory(tests)
endif()
```

`cmake/uniffi_bindgen_cpp.cmake` defines `uniffi_generate_cpp_bindings()` which:
1. Runs `cargo install --git https://github.com/NordSecurity/uniffi-bindgen-cpp --tag ${GENERATOR_TAG} --root ${CMAKE_BINARY_DIR}/uniffi-bindgen-cpp` once (cached on rebuild).
2. Adds an `add_custom_command(OUTPUT ${OUTPUT_HEADER} ${OUTPUT_SOURCE} COMMAND ... --library $<TARGET_FILE:${TARGET}> --out-dir ${OUT_DIR} DEPENDS ${TARGET})` so generation reruns whenever the staticlib changes.
3. Marks the outputs as `GENERATED` for downstream targets.

Library mode is used (rather than UDL mode) because `loro-ffi`'s `uniffi.toml` only configures Swift-specific knobs that are irrelevant for our C++ output.

## Milestones

| Milestone | Scope | Why this scope |
|---|---|---|
| **M1 — pipeline green** | Shim crate compiles. Corrosion imports it. `uniffi-bindgen-cpp` runs and emits `loro.hpp`/`loro.cpp`. CMake links everything. One smoke test (`LoroDoc` + `LoroText` + snapshot round-trip) passes. | The hard part is the build wiring, not the API. Once green, everything else is "write a test, regenerate." |
| **M2 — full surface tests** | One test file per UDL interface (`LoroDoc`, `LoroText`, `LoroMap`, `LoroList`, `LoroMovableList`, `LoroTree`, `LoroCounter`, `LoroAwareness`, `EphemeralStore`, `UndoManager`, `FractionalIndex`, `VersionVector`/`Frontiers`, JSON path). Subscription/event tests with raw `std::function` callbacks. | Confirms generated bindings actually work for each surface; surfaces any UniFFI quirks early. |
| **M3 — `loro_ext.hpp` ergonomics** | Hand-written header on top of generated bindings: `LoroDoc::subscribe_lambda(...)`, `LoroValue::from(std::string)` / `to_string()` shortcuts, `insertContainer<LoroText>(map, key)` template overloads, `expected<T, LoroError>` adapters for fallible methods. Mirrors what `loro-cs` adds to its base. | Without this, the generated API is correct but verbose — UniFFI-flavored, not C++-flavored. |
| **M4 — packaging + CI** | `install()` rules, `loroConfig.cmake` for `find_package(loro)`, optional `pkg-config`. GitHub Actions matrix: Ubuntu 22.04 / macOS-latest / Windows Server 2022 × {gcc, clang, msvc} × {Debug, Release}. Examples build green in CI. | Reproducible consumer integration is the deliverable. |
| **M5 — upstream tracking (deferred)** | When `uniffi-bindgen-cpp` ships a release pairing with the uniffi version `loro-ffi 1.11.x` uses, bump the version triple. | Pure version bumps; no design work. |

## Verification

After M1:
```bash
cmake -S . -B build -DBUILD_TESTING=ON
cmake --build build -j
ctest --test-dir build --output-on-failure
```
The smoke test confirms a `LoroDoc` → text edit → `export_snapshot` → import into a fresh doc → readback round-trip works end-to-end. Generated `loro.hpp` is browsed manually to sanity-check that all 23 UDL interfaces are present.

After each subsequent milestone:
- M2: every UDL interface has at least one test that exercises a non-trivial method.
- M3: `loro_ext.hpp` tests exercise lambda subscriptions, `LoroValue` conversions, and templated container creation.
- M4: a downstream consumer project (in `examples/consumer-fetchcontent/`) consumes `loro::loro` via `FetchContent` from a fresh clone — proves the install + config files work.

Memory: `valgrind` clean on Linux smoke tests; ASan run on the same suite to catch UAFs across the FFI boundary (UniFFI's shared-pointer model makes these unlikely but worth a one-time check).

## Risks & open questions

- **Version-triple drift.** Highest risk. Mitigation: pin all three versions explicitly in `Cargo.toml`, `cmake/uniffi_bindgen_cpp.cmake`, and CI; document the bump procedure in `README.md`. CI fails fast if any drift occurs.
- **`uniffi-bindgen-cpp` is third-party (NordSecurity).** Last release Sep 2025. If abandoned, fallback is to fork the generator or pivot to the cbindgen plan. Vendoring the generator binary in CI artifacts gives a long backstop.
- **Force-link incantations vary by linker.** The `-Wl,--whole-archive` / `-force_load` / `/WHOLEARCHIVE` block is necessary because the staticlib's `#[no_mangle]` symbols would otherwise be GC'd. CI matrix exists specifically to catch any link regressions across toolchains.
- **No async, no external types.** `uniffi-bindgen-cpp` documents these as unsupported. `loro-ffi` doesn't appear to use either, but if a future upstream version introduces async methods (e.g. for network sync), those specific methods will be missing from the generated C++ until the generator catches up.
- **One Loro minor version behind.** `loro-ffi 1.10.3` vs current `1.11.2`. Diffing the two `loro.udl` files on the day of writing the plan tells us whether any new surface in 1.11 is critical; if yes, escalate to building a `uniffi-bindgen-cpp` fork against uniffi 0.31.
